# ADR 0030: 変化量の評価の修正（丸めの順序とキャッシュの同一性）

ステータス: 採択（未実装）

## 文脈

[ADR 0029](0029-variation-deltas.md) の引き継ぎ調査を、コミット `0560f9ca2202c66c9531c625115db3bb985962d8` の草稿と基準のソースを照らして再開した。
[ADR 0027](0027-variable-fonts.md) と [ADR 0029](0029-variation-deltas.md) は提案のままコミット済みである。
そのため、本文を直接直さず、この ADR に修正を記録する。
この提案の採択は、[ADR 0027](0027-variable-fonts.md) 全体の採択を意味しない。

変化量とは、正規化した可変フォントの座標に応じて、メトリクスや輪郭に加える差分である。
ItemVariationStore は、軸ごとの有効範囲を表す領域と、領域に対応する整数の差分の行を持つ。
領域の係数は、その範囲と座標から求める重みである。
`outer` は ItemVariationData の番号、`inner` はその中の行の番号とする。

共通の行の読み取りと、位置ごとに係数を一度だけ求める方針は残す。
これは作成元のフォントに対する係数の保存を指し、作成元の無い静的な既定位置と別フォントへの適用は例外とする。
ただし、算術の丸め、空の座標の扱い、キャッシュを再利用できる条件を次のとおり修正する。

| [ADR 0029](0029-variation-deltas.md) の記述 | 再確認した問題 | この ADR での扱い |
| --- | --- | --- |
| 軸ごとに係数を求めてから掛ける | FreeType は累積値に直接 `FT_MulDiv` を適用する。独立した係数を先に丸めると結果が違う | 累積値を受け取る軸の評価にする |
| 目録などの FNV-1a が同じなら同じフォント | 目録、長さ、`checkSumAdjustment` が同じでも、領域の本文は違いうる | 生存期間を持つ元データの参照とフェイス番号で判定する |
| 座標がすべて0なら、ピークがすべて0の領域だけが1 | FreeType は不正な領域のピークも0にする。さらに CFF2 は空の座標と明示した0座標で異なる | 座標の有無と、評価器ごとの分岐を保持する |
| gvar の `start == peak == coord` で FreeType は0 | FreeType も `peak == coord` を先に調べるため1 | 両方1の境界テストにする |
| gvar の差分を `A::Coord` に保持する | `HbF32::Coord` は正規化座標の `i32` で、点の差分の `f32` と異なる | 座標の型と点の差分の型を分ける |
| CFF2 に係数が0でない列だけ渡す | オペランド数には0の列も必要で、HarfBuzz は0の係数の積も計算する | 列数と0を含む係数を渡す |

丸めの違いは、正の整数の `FT_MulDiv(a,b,c) = floor((a*b + floor(c/2))/c)` で再現できる。
2軸の比率を順に `1/2` と `1/6` とすると、FreeType の累積値は `32768`、`5461` となる。
一方、2軸目の係数を先に16.16へ丸めると `10923` になり、`FT_MulFix(32768,10923)` は `5462` となる。
これは性能上の違いではなく、出力の違いである。

基準は HarfBuzz 15.1.0 と FreeType 2.15.0 とする。
以下のソース位置は、末尾に記したコミットの位置である。
上の数値は整数式の再現であり、フォントを使った適合テストの実行結果ではない。

## 実装すること

### 採択時と実装時の扱い

この ADR を採択したとき、[ADR 0029](0029-variation-deltas.md) のステータスに「評価の修正案は ADR 0030」を、[ADR 0027](0027-variable-fonts.md) のステータスに「変化量の評価と Location の生存期間の修正案は ADR 0030」をリンク付きで追記する。
両方の「提案」は、本人が採択するまで残す。
両方の本文にある `font_key`、共通の gvar 適用器、疎な列のキャッシュは、以下の決定に読み替える。
[ADR 0029](0029-variation-deltas.md) の「[ADR 0027](0027-variable-fonts.md) は未コミットなので改める」という手順は実行しない。

実装には、[ADR 0027](0027-variable-fonts.md) の座標の作り方と問い合わせの移動の採択が前提となる。
採択後は、読み取り、係数の評価、`Location` への組み込み、gvar、C ABI と適合テストの順に進める。
[ADR 0029](0029-variation-deltas.md) の計測と、下記の修正を加えたテスト設計は引き継ぐ。
実装の PR では README、仕様書、API ガイドと対応する C ABI を同時に更新する。

### アルゴリズム：ItemVariationStore の評価

`sofel-font::var` に、行を読む共通の処理 `item_delta` と、封印した算術のトレイト `Arith` を置く。
外部クレートは `Arith` を実装できず、`HbF32`、`HbF64`、`Ft` の3つだけを使う。
型と役割は次のとおりとする。

| 方針 | 座標 | 領域の係数 | 行の積和 | 行の結果 |
| --- | --- | --- | --- | --- |
| `HbF32` | 2.14の `i32` | `f32` | `f32` | `f32` |
| `HbF64` | 2.14の `i32` | `f32` | `f64` | `f64` |
| `Ft` | 16.16の `i32` | 16.16の `i32` | `i64` | `i32` |

軸の評価は `fold_region_axis(acc, coord, start, peak, end)` とする。
`acc` は、それまでの軸を評価した累積係数である。
軸の順序は表の順とし、初期値を1、累積係数が0なら打ち切る。
HarfBuzz は基準と同じ順で `f32` の比率を求め、累積係数に掛ける。
FreeType は、独立した軸の係数を作らず、累積係数を第1引数にして `FT_MulDiv` を一度だけ呼ぶ。
不正な領域の扱いと分岐の順も、各方針が持つ。

行の評価は、列を元の順に読み、係数が0の列を飛ばして積和を取る。
`HbF64` も領域の係数は `f32` で求め、積和の前に `f64` に広げる。
`Ft::finish` は、基準の `FT_INT64` 経路に合わせ、`((acc + 0x8000) as i32) >> 16` とする。
和の上限は、最大65535列、差分の絶対値が最大 `2^31`、係数が `0..=65536` なので `2^63` 未満であり、丸め用の加算も `i64` に収まる。
他の整数変換では、読み取りの検査と明示した切り落としを混同しない。

表の読み取りは `sofel-read` が担当する。
`ItemVariationData::delta(inner,column)` は、`LONG_WORDS` を除いた `wordDeltaCount` と列番号からバイト位置を求める。
位置と長さの計算は checked 演算を使い、切れた行は `None` とする。
`outer`、`inner` が範囲外の場合と `0xFFFF/0xFFFF` は差分0、読めない行も差分0とし、検証器では切れた行を Error にする。
この0は、FreeType のフェイスを開く段階のエラーを消すものではない。
FreeType の公開問い合わせでの表の拒否は [ADR 0027](0027-variable-fonts.md) の方針に従う。

公開の `Instance::item_delta::<A>` は `Result<A::Delta, VarError>` を返す。
`Ft` を選んだ場合の位置のエラーは `VarError::FtLocation` として `Location::ft_error()` の原因を返し、表の評価に入らない。
HarfBuzz の2方針は、この FreeType 側だけのエラーでは止めない。
ストアなしと範囲外番号は `Ok(0)` であり、行を読む内部の `item_delta` と同じ扱いとする。

### データ構造：係数の保存と再利用

`StoreScalars<S>` は領域番号順の `regions: Vec<S>` と、全領域の係数が0かを示す `all_zero: bool` だけを持つ。
ItemVariationData ごとの列は複製しない。
評価時に、表の `regionIndices` を列順に読み、対応する係数を引く。
`all_zero` なら差分の行を読まず0を返し、そうでなければ係数0の列だけ飛ばす。

この形では、係数の記憶量は領域数に比例する。
[ADR 0029](0029-variation-deltas.md) の `columns` と `ranges` は採らない。
同じ ItemVariationData を多数のオフセットが参照する入力でも、列のリストを参照回数だけ複製しないためである。
疎な列の索引が必要かは計測で判断し、必要なら別の ADR で上限とともに定める。

`Location<'data>` は、座標と係数に加え、作成元の `SourceFont<'data> { data: &'data [u8], face_index: u32 }` を保持する。
既定の空の位置だけは作成元を `None` とする。
`Font<'data>` は同じ元データとフェイス番号を確保なしで保持する。
`font_key` は追加しない。

係数を再利用する条件は、元データのスライスが `core::ptr::eq` で同じ開始アドレスと長さを持ち、フェイス番号も一致することである。
元データの借用は `Location` の生存中続くため、元データを解放して同じアドレスを再利用することは、安全な Rust ではできない。
同じバイト列の別のコピーは一致とせず、`OnTheFly` で対象フォントから係数を求める。
同一性の判定は出力に影響せず、キャッシュの使用だけに影響する。

`Instance` は、フォントと位置への参照を別々の生存期間で持つ。
作成元と利用先のフォントの生存期間を同じにする必要はない。
たとえば `Instance<'font, 'data, 'loc, 'source>` は、`&'font Font<'data>` と `&'loc Location<'source>` を持つ。
静的な空の位置は `Location<'static>` であり、任意のフォントと組み合わせられる。

`OnTheFly` はクレート内の処理とし、保存した係数と同じ軸の評価関数を使う。
別フォントへの適用では、保存された正規化座標をそのまま使い、設計座標から正規化し直さない。
足りない軸は0、余った軸は無視する。
gvar の共有の組の係数も、作成元が一致するときだけ再利用する。
avar 版2では、写像前の座標で評価するので `OnTheFly` を使う。

### 空の座標と明示した0座標

位置には、`ft_coords_supplied: bool` を保持する。
静的な既定の位置では偽、軸を持つフォントで位置の構築子が成功した場合は真とする。
軸の無いフォントでは偽とする。
これは、名前つきインスタンスの選択と正規化座標から決める `ft_default` とは別の値である。
FreeType 側にエラーのある位置は、FreeType の問い合わせで [ADR 0027](0027-variable-fonts.md) の `ft_error` を先に返し、係数の評価に入らない。

位置の構築子の比較対象は、新しく開いたフェイスで `FT_Get_MM_Var` を呼んでから、[ADR 0027](0027-variable-fonts.md) が対応付けた座標の設定関数を呼ぶ手順に統一する。
`FT_Get_MM_Var` が作る blend の有無によって、全0の正規化座標を設定するときの早期終了が変わるためである。
静的な既定位置の比較対象ではこの準備を行わず、各問い合わせのために新しいフェイスを使う。
この手順の指定は [ADR 0027](0027-variable-fonts.md) の構築子と適合テストへの追加であり、任意の呼び出し履歴を持つ可変な FreeType フェイスの再現はしない。

FreeType の ItemVariationStore と CFF2 の評価では、この印が偽なら差分と領域の係数は0とする。
CFF2 の既定成分 `BV[0]` だけは16.16の1である。
印が真なら全座標が0でも領域を評価し、不正な領域のピークの置換も行う。
HarfBuzz の MVAR は空の座標でも各軸を0として評価する。
したがって、`Location::default_ref()` や C ABI の NULL を「すべての問い合わせが0」と定義しない。
送り幅、VariationIndex、COLRなど、呼び出し側固有の評価を飛ばす条件は [ADR 0027](0027-variable-fonts.md) の各問い合わせに残す。

CFF2 の FreeType の経路では、座標がある場合にストアの軸数と座標数が異なればエラーとする。
範囲外の `vsindex` と領域番号もエラーとする。
これは一般の ItemVariationStore で範囲外を0にする処理とは分け、既存の `BlendWeights::regions` が返す失敗を保存する。

### CFF2 と gvar

CFF2 の `blend_scalars` は、元の列数と、0を含む列順の係数を返す。
戻り値は `Result<BlendScalars<A>, BlendError>` とする。
`BlendScalars` は `len()` と、列順の `A::Scalar` を返す長さ既知のイテレータを持ち、空の正常な列とエラーを区別する。
`BlendError` はストアなし、読めないストア、軸数不一致、範囲外の `vsindex`、範囲外の領域番号を区別する。
`Ft` の場合は位置のエラーも `BlendError::FtLocation` として返す。
`BlendWeights::regions` のアダプタではエラーを `None` にする。
C ABI ではストアなしと範囲外の `vsindex` を `SOFEL_ERROR_INVALID_ARGUMENT`、読めないストア、軸数不一致、範囲外の領域番号を `SOFEL_ERROR_INVALID_FONT` とする。
位置のエラーは位置の構築時のエラーコードを返す。
Rust の係数列には既定成分を含めず、C ABI の BV 出力だけが先頭の1を補う。
FreeType の `BlendWeights` アダプタは、差分の列数と列番号に対応する係数を渡す。
既定成分は既存の解釈器が別に扱い、差分の列数から必要なオペランド数を検査する。
HarfBuzz の `blend_deltas` は列順にすべての積を `f64` で足す。
係数0の列を飛ばす変更はしない。
CharString の算術で非有限値が生じるかにかかわらず、積を省く同値性の証明を実装の前提にしない。

CFF2 の読み取り層から `sofel-font` への依存は追加しない。
`sofel-font` 側のアダプタが `BlendWeights` を実装し、既存の解釈器に渡す。
既存の `sofel-read::cff::FtBlend` は削除せず、既定座標を使う現在の呼び出しとの互換性を保つ。
新しい `Instance` の経路でアダプタを使い、両者の係数の一致をテストする。

一方、gvar の適用全体を1つの算術トレイトで共有する決定は採らない。
HarfBuzz の `orig_points` は最初の部分的な点指定で保存され、FreeType の `points_org` は組のループの前に固定される。
元の点の保存、直接加算、`flush`、IUP（明示されていない点の差分の補間）の制御まで同じとする根拠はない。
復号ビューと係数の保存を共有し、適用は `apply_hb` と `apply_ft` に分けて基準の順序を保つ。

`apply_hb` は `f32` の点と差分を、`apply_ft` は固定小数点の元の点と差分を持つ専用の作業領域を使う。
正規化座標の型を点の差分に流用しない。
各軸の組の係数も累積値を受け取り、基準の分岐の順を保つ。
`start == peak == coord != 0` なら、両方とも累積係数を変えない。
HVAR/VVAR による幻の点の補正の抑制と最後の点の丸めは、各基準の段階で行う。

HarfBuzz の計算予算も移植する。
グリフ単位の入口で `2^24` を初期値とし、合成グリフと gvar で同じ予算を受け渡す。
gvar の有効な組では、全点の処理なら点数、幻の点だけなら4を基準と同じ位置で引く。
予算が負になれば失敗を返し、途中の点を正常な輪郭として公開しない。
ビューの境界検査を計算予算の代わりにしない。

### C ABI

[ADR 0029](0029-variation-deltas.md) の ItemVariationStore の2関数と、FreeType の blend vector の関数を残す。
`location == NULL` は静的な既定位置として扱い、HarfBuzz の MVAR を含む結果を Rust と一致させる。
`font`、結果のポインタ、列挙値の検査は既存の C ABI の規約に従う。

位置は作成元データを借用するため、C の呼び出し側は `sofel_location_destroy` まで元データを生かし、不変に保つ。
作成元の `sofel_font_t` 自体は先に破棄してよい。
別フォントに位置を使う場合も、作成元のデータの寿命は短くならない。
この条件をヘッダと API ガイドに書く。

blend vector は `BV[0]` を含む必要長を返す。
出力容量が足りなければ、出力配列を変更せず `SOFEL_ERROR_BUFFER_TOO_SMALL` を返す。
長さだけを調べる場合は、出力ポインタの NULL と容量0を認める。
長さの出力ポインタの NULL はエラーとする。
この NULL の例外もヘッダに明記する。

## 実装しないこと

- [ADR 0027](0027-variable-fonts.md) と [ADR 0029](0029-variation-deltas.md) の本文の書き換え、およびレビュー前の採択。
- gvar の2つの適用器を、出力の一致を確かめずに統合すること。
- フォント全体のハッシュ、アドレスの整数化、グローバルな連番、内部可変性による識別。
- 領域ごとの係数の遅延計算、送り幅と縦の原点の結果のキャッシュ。
- VARC、ヒンティング、任意位置へのサブセットのインスタンス化。行き先は [ADR 0027](0027-variable-fonts.md) のままとする。

## 不変条件

以下の条件は、この ADR の実装のテストで番号を名前に含める。
浮動小数点の比較は、有限値、符号付き0、無限大ではビット一致、NaN では双方が NaN であることとする。
NaN のペイロードまでの環境間一致は約束しない。

1. **I01 算術**：各軸を評価した累積係数と行の結果は、同じ座標と領域と行を与えた基準の算術と一致する。
2. **I02 保存の透過性**：保存した係数と `OnTheFly` の評価は、同じ対象データ、正規化座標、座標の有無に対して一致する。
3. **I03 別フォント**：元データまたはフェイス番号が異なれば、ItemVariationStore と gvar の保存した係数を使わず、対象フォントから求めた結果になる。
4. **I04 既定位置**：空の位置と明示した0座標は、それぞれ対応する基準の操作と一致する。両者が等しいとは仮定しない。
5. **I05 読み取り**：範囲外の行と読めない行は差分0、範囲内の完全な行は宣言された幅で読む。どちらでも境界外アクセスと panic がない。
6. **I06 列の保存**：CFF2 の係数列の長さは元の列数と等しく、0の列と重複した領域番号も元の位置を保つ。
7. **I07 gvar**：各適用器の点と失敗の結果は対応する基準と一致し、幻の点だけの経路は全点の経路の幻の点と一致する。ただし予算切れの成否は各経路の費用に従う。
8. **I08 C ABI**：有効な引数では Rust と同じ値を返す。出力容量不足では必要長を返し、出力配列を変更しない。
9. **I09 記憶量**：係数の保存領域の要素数は、領域数と共有の組の数の和に比例し、ItemVariationData の参照回数では増えない。
10. **I10 予算**：HarfBuzz の経路では、必要費用と残予算が等しければ処理を認め、一つ足りなければ失敗とする。失敗した呼び出しは途中の点を成果物として返さない。

| 境界の入力 | 期待する結果 | 条件 |
| --- | --- | --- |
| 領域0、行0、列0 | 読める空の表は差分0 | I01、I05 |
| 1領域、1行、1列、係数1 | 整数の差分を方針の型で返す | I01 |
| 軸の比率が順に `1/2`、`1/6` | FreeType の係数は5461。5462ではない | I01 |
| 行がちょうど収まる／末尾が1バイト欠ける | 前者は評価、後者は差分0と検証 Error | I05 |
| `inner == itemCount-1`／`inner == itemCount` | 前者は最終行、後者は0 | I05 |
| 座標なし／明示した0座標、全ピーク0 | FT の係数は前者0、後者1。HB の生の領域評価は双方1 | I04 |
| `start < 0 < end`、非0ピーク、座標0 | HB の係数0、FT は座標があれば1 | I01、I04 |
| gvar の `start == peak == coord != 0` | 両方とも累積係数を維持 | I01、I07 |

## 計測

領域の係数を先に求める方針は維持する。
構築時間と係数の記憶量、HVARの全グリフの送り幅、GDEFを使うシェーピング、gvar、既定位置の既存処理を [ADR 0029](0029-variation-deltas.md) と同じフォントで測る。
別フォントと同じ内容の別コピーは `OnTheFly` になるため、その場合も分けて記録する。
静的な既定位置の MVAR も `OnTheFly` であり、その問い合わせの費用を独立した項目として測る。
性能の予想を達成済みの数値として記録しない。

## トレードオフ

元データを借用することで、ハッシュの衝突とアドレス再利用を正しさの問題から除ける。
代わりに、位置が元データの寿命に依存し、C の呼び出し側にも寿命の条件が増える。
元データ全体のコピーと全体比較は、位置ごとの記憶量と問い合わせの費用が増えるため採らない。

密な領域の係数だけを保存すると、非0列だけのリストより問い合わせ時の走査が増える。
代わりに、記憶量がストアの参照の重複で増えず、評価とキャッシュの構築が同じ列のビューを使える。
gvar は2つの適用器を保つため制御の重複が残るが、丸めと点の保存の順序を基準の関数に対応させられる。
