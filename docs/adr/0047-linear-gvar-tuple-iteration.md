# ADR 0047: gvar の組を線形に走査する

ステータス: 採択

## 文脈

[ADR 0029](0029-variation-deltas.md) は、gvar の組を記録順に適用する。[ADR 0030](0030-variation-evaluation-corrections.md) は、HarfBuzz と FreeType の算術を分けながら、同じ組の列を使う。現在の `GlyphVariationData::tuple(i)` は、組 `i` を返すたびに最初の組からヘッダを進める。`apply_hb`、`apply_ft`、`apply_hb` の私用の点の有無の確認は、組の番号を順に増やしてこの関数を呼ぶ。組が `n` 個あるグリフでは、ヘッダを読む回数が `n(n+1)/2` になる。

組ごとの算術、IUP、HarfBuzz の `flush` の順序は変えない。改善の対象は、組ヘッダと直列化された差分の位置を探す操作である。

## 実装すること

- `sofel-read::gvar::GlyphVariationData` に、次のヘッダ位置と差分位置を持つ借用イテレータを足す。イテレータは組を記録順に一度ずつ返し、前の組の末尾から次の組へ進む。組の値を並べた配列は作らない。
- `sofel-font::var::gvar::apply_hb` の私用の点の確認と組の適用、`apply_ft` の組の適用をイテレータへ移す。私用の点の確認が必要な HarfBuzz の経路は二度走査する。両方とも組数に比例するヘッダ走査にする。
- `GlyphVariationData::tuple(i)` は、既存のランダムアクセス用 API として残す。既存の呼び出し側の結果と誤りの扱いは変えない。

## 実装しないこと

- gvar の差分の算術、IUP、HarfBuzz の `flush`、FreeType の差分の和、係数キャッシュ、点の作業領域は変えない。
- 組のヘッダや差分を位置ごとに保存する索引を足さない。
- 検証器の診断の種類と順序は変えない。検証器の `tuple(i)` 呼び出しを移す場合も、診断が同じであることを先に確かめる。

## 不変条件

1. I01: 有効なグリフデータのイテレータは、`tuple_count()` 個の組を記録順に返し、各組の公開された値が `tuple(i)` と等しい。
2. I02: 空の組列は何も返さず、一つの組は一度だけ返す。二つ以上の組では、差分のスライスが隣の組へずれない。
3. I03: 有効な gvar に対する `apply_hb` と `apply_ft` の結果は、組を番号で引く実装と等しい。係数が 0 の組と私用の点を持つ組を含む場合も等しい。
4. I04: 破損したオフセット、組ヘッダ、差分の入力は、従来と同じ `None`、`GvarError`、診断を返し、panic しない。
5. I05: 一回の走査で進めるヘッダ位置と差分位置は後戻りせず、走査用の確保量は組数に依存しない。

| 境界の入力 | 期待する結果 |
| --- | --- |
| 組が 0 個 | イテレータは 0 個返す |
| 組が 1 個 | `tuple(0)` と同じ 1 個を返す |
| 組が 2 個 | 2 個を順序と差分の境界を保って返す |
| 最後の組の差分がちょうど収まる | 最後の組を返して終了する |
| 最後の組の差分が 1 バイトあふれる | グリフデータの読み取りが失敗する |
| 組ヘッダが途中で切れる | グリフデータの読み取りが失敗する |

## テスト設計

まず、手で組んだ 0、1、2 個の組と、ヘッダと差分の境界が壊れたグリフデータで I01、I02、I04 のテストを書き、失敗を確認する。次に、HarfBuzz の私用の点と係数 0 を含む組列を `HbF32` と `Ft` に適用し、既存の期待値と比べて I03 を確かめる。

イテレータのカーソルの単調増加と、走査中に組ごとの配列を作らないことを I05 の単体テストとコードの確認で確かめる。破損バイト列の既存の gvar fuzz 対象を実行し、panic がないことを確かめる。

最後に、同じビルドと同じ可変フォントの全グリフについて、既定位置と非既定位置の箱の時間を変更前後で測る。速度の判断には全グリフを返し終える時間を使い、結果の箱を HarfBuzz と照合する。計測結果はこの ADR に追記せず、新しい benchmark 記録に残す。

## トレードオフ

HarfBuzz の私用の点の確認は組の適用より前に必要なので、ヘッダを二度読む。一度目の結果を配列に保存する方法よりメモリ使用量を小さくできる。二度の線形走査でも、組数が増えたときのヘッダ走査は二次ではなく一次で増える。

`tuple(i)` を残すので、ランダムアクセスを求める呼び出し側の時間は変わらない。順に読む呼び出し側だけが新しいイテレータを使う。
