# ADR 0051: シェーピングの作業バッファは現状の28バイトを認める

ステータス: 採択（未実装）

## 文脈

[ADR 0020](0020-shaping-foundation.md) は、作業バッファの各要素に工程ごとのフィールドを設け、まず1要素を20バイトに収めるとした。
この要素を表す内部型が、シェーピング中に文字やグリフの情報を保持する `Info` である。

## 調査した事項

`Info` は正規化で選んだグリフ番号を `glyph_index` に保持する。
シェーパーが使う分類、位置、補助値にも、それぞれ独立したフィールドがある。
位置情報を格納する `Pos` は別の型である。

`cargo test -p sofel-shape --lib buffer::tests::item_sizes -- --exact` を実行し、1件が成功した。
このテストは `size_of::<Info>() == 28` と `size_of::<Pos>() == 20` を検査する。
[仕様書](../specifications.md)では、作業バッファの説明に24バイト、シェーパーの説明に28バイトと記載している。
[ロードマップ](../roadmap.md)の24バイトも現在の `Info` のサイズと食い違う。

## 実装すること

[ADR 0020](0020-shaping-foundation.md) の20バイトという初期目標を見直し、現在の28バイトの構造を認める。
採択時に仕様書の作業バッファの説明を28バイトに訂正し、ロードマップに判断結果を反映する。

## 縮小案を検討するときの計測

将来、縮小案を検討するときは、現在の構造と候補の構造で同じ入力をシェーピングする。
[ADR 0006](0006-performance-measurement.md) に従って条件をそろえ、要素のサイズとシェーピングの実行時間を記録する。
縮小を採用するかは、その計測結果に基づいて判断する。

## 実装しないこと

今回の対象にフィールド配置の変更や縮小案の実装は含めない。

## 不変条件

なし。この決定は内部型の現状のサイズを認め、将来の見直しの手順を定めるもので、入力に応じた振る舞いを変更しない。

## テスト設計

現状のサイズは「調査した事項」に示した既存テストで確かめる。
縮小案を計測する際は、同じ入力についてグリフ列と位置が現行の結果と一致することも確かめる。

## トレードオフ

工程ごとのフィールドを分けておくと、正規化や各シェーパーが使う値をフィールド名で追える。
一方、28バイトの要素を配列に並べると、20バイトの場合に比べて1要素につき8バイト多く使う。
実行時間への影響は今回のサイズ検査からは分からない。
