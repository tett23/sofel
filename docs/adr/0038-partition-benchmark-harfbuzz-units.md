# ADR 0038: 計測用 HarfBuzz の翻訳単位を分割する

ステータス: 採択

## 文脈

[ADR 0013](0013-benchmark-harness.md) の計測用 HarfBuzz は、固定したソースを一つの翻訳単位でコンパイルする。
翻訳単位は、コンパイラが一度の呼び出しで処理するソースのまとまりである。
現在はサブセット化も含む `src/harfbuzz-subset.cc` が74個の `.cc` を取り込む。
一方、[ADR 0033](0033-ci-latency-and-ligature-iteration.md) は native と wasm のビルドを並行して走らせる。
大きな翻訳単位のコンパイルが重なるため、メモリの保持量が増えた。

ユーザーは、ビルドを直列に戻さず、アルゴリズムとデータ構造を変えてメモリを減らすよう求めた。
`harfbuzz-subset.cc` が指定するソースとコンパイラのフラグを保ち、翻訳単位だけを分ける。
コンパイラは一つの翻訳単位の処理後に終了するため、その構文木と最適化中の表現を次の翻訳単位まで保持しない。

ローカルの試行では、native と wasm の2並列のまま、C ビルドの合計 RSS の最大観測値が3,186,528 KiBから2,005,680 KiBへ37.1%減った。
時間は51.40秒から68.78秒へ17.38秒増えた。
CI の cold の既測では `bench` と最長の macOS 適合テストの実行時間の差は179秒だったが、ローカルの増分が CI でもこの余裕に収まるかは未確認である。

## データ構造とアルゴリズム

`bench/split-harfbuzz.awk` は、元のファイルの各行を順に読む。
受け付ける行は、現在の HarfBuzz の生成物と同じ `#include "相対パス.cc"` の形とする。
プリプロセッサの条件や定義を任意の位置で分けることはしない。
空の入力と、この形でない行がある入力は失敗にする。

全行を確認してから、行数を `n`、組数を `min(4, n)` とする。
0から始まる行番号 `i` の組は `floor(i × 組数 / n)` で決める。
同じ組の連続した行を一つの `.cc` ファイルに書く。
74行の場合の組の大きさは19、18、19、18行となる。
保持するのは取り込む行の一覧であり、各 `.cc` の中身をコピーするものではない。

## 実装すること

`bench/build-c.sh` は、各ターゲットのビルドごとに空の作業ディレクトリへ翻訳単位を生成する。
同じ `-O2`、C++11、例外と RTTI を無効にする指定、スレッドに関する指定、include ディレクトリで各単位を順番にコンパイルし、同じ `libharfbuzz.a` に収める。
`HB_NO_MT` は従来どおり wasm にだけ定義する。
FreeType と計測用 shim のビルドは変えない。

native と wasm のビルドは並行のままとし、各ターゲット内でコンパイラを並行して増やさない。
パーティションを生成するスクリプトも CI の計測用 C ライブラリのキャッシュキーに含める。
変更後の初回は再ビルドし、同じ入力のキャッシュがある回はこれまでどおり復元する。

## 実装しないこと

- `tools/hb-dump` の翻訳単位の変更。これは内部の関数を使う別の参照ツールである。
- C と C++ の最適化レベル、固定した外部ソース、機能を選ぶマクロの変更。
- native と wasm のビルドの直列化、テストの省略、測定項目の削減。
- 過去の計測記録の修正と、翻訳単位を変えた後も参照側の実行時間が同一だとすること。
- 変更後の CI の前に、workflow 完了時間の維持を実証したとすること。

## 不変条件

1. 妥当な `n > 0` 行の入力は `min(4, n)` 個の空でない組に分かれ、最大と最小の行数の差は1以下となる。
2. 組を番号順に連結した include 行の内容と順序は元の入力と一致する。
3. 空の入力、相対パスの `.cc` の include 以外の行を含む入力は非ゼロで終了し、部分的な翻訳単位を残さない。
4. 固定した入力とフラグのもとで、native と wasm の `hb_*` 外部シンボルの集合は分割前と一致し、両ターゲットの計測用 `--once` の全照合が成功する。

| 入力 | 組数 | 結果 |
| --- | ---: | --- |
| 空 | 0 | 失敗 |
| include が1行 | 1 | 1行の組 |
| include が4行 | 4 | 各組1行 |
| include が5行 | 4 | 2、1、1、1行 |
| 固定した74行 | 4 | 19、18、19、18行 |
| 未対応の `#define` または絶対パスを含む | 0 | 失敗 |

## テスト設計

`scripts/tests/test-adr0038-i1-i3-harfbuzz-units.sh` は境界の入力を生成し、組数、各組の行数、連結した行の一致と、失敗時に結果を残さないことを検査する。
生成スクリプトを実装する前にこのテストを実行し、妥当な入力を分割できず失敗することを確認する。

不変条件4の手動検査 `adr0038_i4_reference_equivalence` は、分割前後のアーカイブを `nm` で読み、`hb_*` の集合を比較する。
それぞれにリンクした実行ファイルで native と wasm の `--once` を走らせる。
参照側の速度は、Roboto の `en-words.txt` のシェーピングと3フォントのサブセット化で、既存の3 warm-up、30標本の中央値と中央絶対偏差を比較する。

## トレードオフ

翻訳単位を分けると、共通のヘッダーを複数回処理するため、コンパイル時間は増えうる。
翻訳単位をまたぐ最適化も変わり、同じソースとフラグでも参照側の実行時間は変わりうる。
試行の代表16項目では分割後の中央値が最小で6.02%短く、最大で4.73%長くなった。
各方式1回なので、すべての項目や環境にこの範囲を保証しない。
過去の記録と比べるときは参照側のビルド条件が変わったことを示す。

採択後の CI では、キャッシュがない回の C ビルドの RSS と実行時間、workflow の開始から最終ジョブ終了までの時間を測る。
キャッシュがある回ではビルドが省かれることも確かめる。
計測用 C ライブラリのキーが変わっただけの回を、すべてのキャッシュがない回とはみなさない。
workflow 全体で cold と warm を比べるときは、既存のキャッシュ世代の仕組みで新しい世代を使い、同じ head の再実行で各キーの復元結果を記録する。
runner の開始待ちとジョブ時間の合計は、workflow 完了時間の代わりにしない。
