# ADR 0033: CI の完了時間と合字候補の走査

ステータス: 採択（未実装）

## 文脈

CI の高速化では、ジョブの時間の合計でなく、workflow が始まってから最後のジョブが終わるまでの時間を短くする。
2026-11-11 に取得した [CI run 42875555732](https://github.com/tett23/sofel/actions/runs/42875555732) では、macOS の `conformance` が631秒で最も長かった。
その内訳は、FreeType の参照ツールのビルドが12秒、HarfBuzz の参照ツールのビルドが86秒、適合テストのステップが406秒だった。
適合テストのステップには Rust のビルド約62秒と、テストの実行約343秒が含まれる。
次に長い Linux の `conformance` は478秒、`bench` は452秒だった。

今の workflow は、参照ツールと計測用の C ライブラリを毎回ビルドする。
また、`conformance` の Cargo キャッシュはレジストリと Git の取得物だけを保存し、コンパイルした Rust の成果物を保存しない。
Cargo はテストの実行ファイルを一つずつ実行するため、異なるテストの実行ファイルの待ち時間は重ならない。

シェーピングの CPU サンプルでは、合字候補の配列の確保と読み取りが目立った。
`crates/sofel-shape/src/layout/gsub.rs` は、対象のグリフごとに `LigatureSet` の読める候補をすべて `Vec` へ集め、その後に最初の一致を探す。
候補の後半を使わない場合も、配列の確保と候補の読み取りが発生する。
採択済みの [ADR 0020](0020-shaping-foundation.md) の順序と一致条件を保ったまま、この仕事を省ける。

ユーザーは、この高速化について ADR より先の着手を許可した。
この ADR と実装は、レビュー前にはコミットしない。
測定コマンドと結果は [性能の記録](../benchmarks/2026-11-11-ci-latency-and-ligatures.md) に残す。

## 実装すること

### CI のビルド成果物

`conformance` は、Rust の release の成果物と三つの生成ツールの Cargo の成果物をキャッシュする。
キーには OS、アーキテクチャ、lock ファイル、Rust のツールチェーンの指定とコミットを含める。
同じ OS、アーキテクチャ、lock ファイルとツールチェーンの直近のキャッシュも復元し、Cargo に更新の判定を任せる。

参照ツールと計測用の C ライブラリは、入力が完全に一致するキーのキャッシュだけを使う。
キーには OS、アーキテクチャ、runner image の名前と版、C と C++ のコンパイラの版の出力、`testdata.lock` と、それぞれのビルドスクリプトとソース、workflow の定義を含める。
計測用のキーには、wasi-sdk の取得スクリプトと lock ファイル、FreeType のモジュールの指定も含める。
キャッシュが当たらなければ、これまでと同じスクリプトでビルドする。
キャッシュの有無にかかわらず、結果の照合は実行する。

キャッシュがない `bench` の回は、`scripts/build-bench-c.sh` でネイティブと wasm の C ライブラリのビルドを並行して実行する。
両方の終了を待ち、一方でも失敗したらステップを失敗させる。
それぞれのビルド内は従来どおり直列とし、同時にコンパイルする大きな HarfBuzz の翻訳単位は最大二つとする。

### 適合テストの実行

`scripts/test-conformance.sh [JOBS]` は、ネイティブの適合テストを最大 `JOBS` 本の実行ファイルで並列に走らせる。
`JOBS` の既定値と CI での値は2とし、正の整数以外は終了コード2で拒む。
1を渡せば、同じ runner で直列の比較ができる。

最初に `cargo test --release -p sofel-conformance --no-run --message-format=json` を実行する。
成功したときだけ、Cargo の JSON にあるテストの実行ファイルを `jq` で取り出し、`xargs` で実行する。
パスを NUL で区切り、空白のあるパスも一つの引数として渡す。
過去のビルドの実行ファイルが混じらないよう、`target/` のファイル名では選ばない。

各実行ファイルはパッケージのディレクトリから起動し、`--nocapture --test-threads=1` を渡す。
libtest のスレッド数を1にすることで、外側の並列数との掛け算を避ける。
テスト自身が明示的に作るスレッドや参照ツールの子プロセスは、そのまま使う。
最後に `cargo test --release -p sofel-conformance --doc` で、実行ファイルの一覧に含まれない doctest を実行する。

### 合字候補の読み取り

合字の候補を、表の順序のまま読む clone 可能な iterator にする。
読めない候補を飛ばす規則は変えない。
HarfBuzz と同じ fast path に入る条件は、生のオフセット数でなく、読める候補が二つ以上あることとする。
この条件は、iterator の clone から読める候補を最大二つ取って調べる。
実際の適用では、最初に一致した候補で走査を終える。

### CI での計測

CI は、参照ツールのビルド、適合テストと計測用 C ライブラリのビルドを `scripts/measure-process-tree.sh` で起動する。
起動したコマンドと子孫の RSS を `ps` から集計し、取得の後に0.1秒待って繰り返す。
最大観測値とサンプル数をログへ書き、計測に失敗しなければ子の終了コードをそのまま返す。
RSS は共有ページも各プロセスで数えるため、物理メモリの使用量や瞬間的な最大値とは限らない。

Actions のキャッシュキーに世代 `adr0033-v1` を加え、既存の共有キャッシュを削除せずに、キャッシュがない最初の回を実行する。
同じ head の workflow を再実行し、各キャッシュの hit と miss をログで確かめて、キャッシュがある回と比べる。
workflow の開始から最後のジョブの終了までの時間は、GitHub Actions の API の時刻から求める。

## 実装しないこと

- テストケース、期待する失敗、ハッシュの照合の削減。
- fuzz の実行時間の短縮。
- 新しいテスト runner の外部パッケージの導入。
- 参照ツールの最適化レベルやコンパイルするソースの変更。
- 合字の選択順、グリフ、クラスタ、フラグ、位置の変更。
- 無制限の並列化。
- CI の実測前に、workflow 全体の短縮率を達成したとすること。

## 不変条件

1. ビルドが成功し、各テストが正常終了する場合、Cargo が返したすべてのテストの実行ファイルを一度ずつ実行し、doctest も実行する。
2. ビルド、JSON の読み取り、実行ファイルのテスト、doctest のどれかが失敗すれば runner は非ゼロで終了する。ビルドが失敗した後にはテストを起動しない。実行ファイルの一覧が空の場合も失敗する。
3. runner が同時に起動するテストの実行ファイルは `JOBS` 本以下であり、各実行ファイルの libtest のスレッド数は1である。
4. 合字の候補を先に配列へ集める実装と、必要なときに読む実装は、読めない候補を含む場合も、同じグリフ、クラスタ、フラグと位置を返す。
5. ネイティブと wasm の C ビルドのどちらかが失敗すれば、両方の終了を待った後にビルドのステップを失敗させる。
6. C の成果物のキャッシュは、列挙したキーの入力がすべて一致した場合だけビルドを省く。成果物の再利用によってテストや結果の照合を省かない。
7. 計測に成功した wrapper は、起動したコマンドの終了コードをそのまま返す。
8. RSS の合計は、起動したコマンドとその子孫だけを含む。

| 境界の入力 | 期待する結果 |
| --- | --- |
| テストの実行ファイルが0本 | 非ゼロ終了 |
| 実行ファイルが1本、`JOBS=2` | 一度だけ実行する |
| 実行ファイルが3本、`JOBS=2` | 同時には2本以下とし、3本とも一度ずつ実行する |
| `JOBS=0`、負数、空文字、小数、非数 | 終了コード2 |
| 子のビルド、テスト、doctest が失敗 | 非ゼロ終了 |
| 空白を含む実行ファイルのパス | 一つの引数として起動する |
| 合字の候補が0個、1個、2個以上 | 0個なら置換せず、1個なら通常の照合、2個以上なら同じ fast path |
| 生の候補が2個で、読める候補が1個 | 1個の候補として扱う |
| 複数の候補が同じ成分に一致 | 表の順序で最初の候補を使う |
| 最初の文字だけがあり、次の文字がない | 候補の照合に失敗し、元と同じフラグを返す |
| C のビルド入力かツールチェーンのキーが変わる | キャッシュでビルドを省かない |
| 計測対象が成功、または非ゼロ終了 | 同じ終了コードを返す |
| 無関係なプロセスが大きな RSS を持つ | 集計に含めない |

## テスト設計

`scripts/tests/test-adr0033-i1-i3-conformance-runner.sh` で不変条件1から3を検査する。
偽の Cargo とテストの実行ファイルを使い、実行回数、同時実行数、引数と各段の失敗を検査する。
このテストは runner を作る前に実行し、runner が存在しないため失敗することを確かめた。

`adr0033_i4_ligature_candidate_order_and_unreadable_candidates` で、不変条件4の境界を検査する。
候補が空、一つ、複数の場合と、null または範囲外のオフセットを先頭と末尾に置く場合を作る。
出力が変わらない最適化のため、この回帰テストは旧実装でも通ることを確かめる。
適合テストの全件と、ネイティブと wasm のシェーピングのハッシュも確かめる。

`scripts/tests/test-adr0033-i5-bench-build.sh` で、不変条件5の二つの子コマンドの成功と失敗の四つの組を偽のビルドで検査する。
このテストも、runner が存在しないため失敗することを確かめてから実装した。
不変条件6は、workflow のキーに列挙した入力が含まれることと、照合のステップにキャッシュによる実行条件がないことを確認する。
`scripts/tests/test-adr0033-i7-i8-ci-measurement.sh` は、偽の `ps` とコマンドで、不変条件7と8の子孫の合計と終了コードの維持を検査する。
このテストは、計測用 wrapper が存在しない状態で失敗することを確かめてから実装する。
レビュー後の CI で、キャッシュがない回と同じ入力のキャッシュがある回を分けて記録する。
runner は同じ入力で直列と2並列を比べ、wall-clock と子プロセスを含む合計 RSS の最大観測値を記録する。
シェーピングは同じベンチマークの入力で変更前後を交互に実行し、照合、中央値と中央絶対偏差を記録する。

## トレードオフ

テストの実行ファイルを2本走らせると、1本の場合よりもメモリを使う。
ただし、各実行ファイルの libtest のスレッドを1に絞り、外側の並列数を2に固定する。
テストが作る子プロセスを含むメモリの実測を残し、runner の空きメモリで安全に走ることを CI でも確かめる。
ジョブ数自体は増やさないため、GitHub Actions の同時ジョブ数の制限による新しい待ち行列を作らない。

キャッシュの保存と復元には時間と容量が要る。
C のキーは runner image の版も含むため、image が変われば再ビルドになる。
正確な失効を優先し、このキャッシュに前方一致の復元キーは付けない。
Rust の成果物は Cargo が入力を検査するので、同じツールチェーンの前のコミットのキャッシュも利用する。

合字の fast path の判定では、最初の読める候補を最大二つ、適用時に読み直す。
一方、候補の配列の確保を省き、早く一致した場合には後半の候補を読まない。
大きな永続キャッシュを加えず、計画とフォントの所有関係も変えない。
