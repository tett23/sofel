# ADR 0035: 直列化の適合テストで参照出力を逐次比較する

ステータス: 採択

## 文脈

[ADR 0033](0033-ci-latency-and-ligature-iteration.md) は、workflow の完了時間を短くするため、適合テストの実行ファイルを最大2本で並列に走らせることにした。
ユーザーは、並列数を維持し、アルゴリズムを変えてメモリ使用量を削減するよう求めた。
この ADR は、HarfBuzz の直列化と復元を照合する適合テストのデータの保持方法を変える。

ローカルで2並列の適合テストの子孫プロセスを途中から観測したところ、合計 RSS の最大観測値1,534,208 KiBの内訳は `raster` が767,632 KiB、`harfbuzz_serialize` が762,240 KiBだった。
その時点の参照用の `hb-dump` は3,072 KiBで、テスト側の二つのプロセスが大部分を占めていた。
この値は全実行期間の最大値ではなく、共有ページの重複を含む RSS の観測値である。

`crates/sofel-conformance/tests/harfbuzz_serialize.rs` は、生成した入力の集まりをバイト列の配列として保持し、エスケープした全入力をさらに一つの文字列にしてファイルへ書く。
その後、`Command::output()` で `hb-dump --deserialize` の全出力を受け取り、比較を始める。
入力と出力の全量を同時に保持する必要はない。
入力の順序を保った逐次書き込みと、状態を持つ行単位の比較に変える。

## データ構造とアルゴリズム

既存の処理は、変異したバイト列の配列、エスケープした全行の文字列、参照プロセスの出力全文を順に作り、比較の間も保持する。
変異の挿入では、元の配列を複製した後に `insert` で後半を移動し、容量が足りなければ再確保する。
次の候補を、保持量、コピー回数と比較の CPU 時間で検討する。

| 候補 | 保持量とコピー | CPU 時間と複雑さ |
| --- | --- | --- |
| 不変な byte arena と範囲の索引 | バイト列を一つにまとめ、個別の確保を減らす。全変異のバイトは残る | 索引の並べ替えと重複除去が要る |
| mmap で予約した領域を自前で管理する arena | 個別の確保を減らし、仮想アドレスの予約と resident なページの量を分けて管理する。全出力の重複保持は別に解消する必要がある | OS ごとの確保、初期化、境界、寿命と解放の管理が要る。未実測で、速度の改善は未確認 |
| 元のバイト列と変異位置の記述 | 各変異の全バイト列を保持しない | 比較のたびに仮想的なバイト列を読み、並べ替えの CPU 時間が増える可能性がある |
| 必要な容量への一度の書き込みと逐次入出力 | 挿入による移動と再確保、エスケープ済み全文、参照出力全文をなくす | 既存の並べ替えと比較を保ちやすい |

まず、必要な容量へ一度だけ書く構造と逐次入出力を比較の基準として実装する。
削除した変異は前半と後半を、挿入した変異は前半、挿入バイト、後半を必要な容量の配列へ順に書く。
元のバイト列は変更しない。
不正な UTF-8 もバイト列としてそのまま扱う。
arena と変異位置の記述は、残る保持量と計測した CPU 時間に見合う場合に追加で検討する。
逐次化後も単体テストの合計 RSS の最大観測値は306,720 KiBだったため、不変な byte arena と範囲の索引を追加で比較した。
生成する全変異のバイト数と件数を先に計算し、二つの配列にそれぞれ必要な容量を確保する。
バイトを一度書いた後は、範囲の索引だけを並べ替えて重複を除き、バイト列を借用してファイルへ書く。
サイズの計算が整数の上限を超える場合は、確保前に失敗させる。
この方式は個別の配列を使う逐次版の306,848 KiBに対して187,584 KiBとなったため、実装する方式に選ぶ。
同じ比較の時間は16.03秒と15.73秒で、各1回の測定から速度の優位までは判断しない。
条件と前後の結果は[計測記録](../benchmarks/2026-11-11-streamed-serialization.md)に示す。
mmap の候補は native のテスト用であり、`no_std` のライブラリ本体や wasm に導入するものではない。
現在の実装は通常の `Vec` と標準の入出力で行い、新しい unsafe は使わない。

## 実装すること

HarfBuzz の出力の比較は `BufRead` から再利用するバッファへ一行ずつ読む。
Unicode、グリフ、直前の直列化結果と行番号の状態を持ち、各行で従来と同じ比較を行う。
参照出力の全量を一つの `String` に保持しない。
HarfBuzz の失敗と読み取りエラーはテストの失敗にする。
直列化の各行の次には対応する復元結果を一つ、生成した入力の各行の次には glyphs と unicode の text と JSON の4結果を要求する。
既知の入力行数、全64 flags と2形式から期待する比較件数を求め、参照出力の不足と余分な行も失敗にする。
`hb-dump` が持つ24個の固定入力の全接頭辞は529件であり、この件数も照合する。

生成した入力は、従来どおり全接頭辞と指定された位置の変異を作り、バイト列の辞書順に並べ、重複を除く。
この集合と順序は変えない。
エスケープした行は `BufWriter` へ一行ずつ書き、全行を合わせた `String` を作らない。
ファイルへの書き込みが完了したら、入力の配列を解放してから参照プロセスを起動する。

比較の件数、期待する失敗の判定と差分の詳細を保つ。
直列化結果から変異用の入力を作る条件も変えない。
CI の並列数、C のビルド、コンパイラのフラグとライブラリ本体には変更を加えない。

## 実装しないこと

- 適合テストと native / wasm の C ビルドを直列に戻すこと。
- テストの入力、比較する項目、参照の呼び出しと期待する失敗を減らすこと。
- HarfBuzz のビルドに使う翻訳単位や最適化レベルの変更。
- 入力の全変異の集合、順序と重複除去の比較順序の変更。
- 輪郭とラスタライズの参照出力の保持方法の変更。

## 不変条件

1. 同じ妥当な参照出力は、読み取りの区切りが異なっても同じ比較件数、失敗件数、詳細と変異生成用の直列化結果になる。
2. 行を比較するときに、後続の全行を読み取って保持する必要はなく、参照出力の保持量は最大の一行と比較状態の大きさに依存する。
3. 出力の読み取りエラーと参照プロセスの非ゼロ終了は、テストの失敗になる。
4. 同じ入力の集合をファイルへ書いたバイト列は、従来の全行のエスケープ結果を連結したバイト列と一致する。
5. 既存の全5フォントで、各比較項目の件数、生成する入力の件数と期待する失敗の判定が変わらない。
6. 変異のバイト列と生成順序は従来と一致し、各配列には必要な長さの容量を一度確保してから前半と後半を書き込む。削除と挿入のために、複製後のバイトを移動したり容量を拡張したりしない。
7. arena の各範囲が指すバイト列と順序は、個別の配列で生成した場合と一致する。並べ替えと重複除去の後も一致し、サイズの計算の整数オーバーフローは確保前に検出する。

| 境界の入力 | 確認すること |
| --- | --- |
| 空の出力 | 比較件数と保持する直列化結果は0 |
| 一行だけの出力 | 状態更新が一度だけ行われる |
| 改行をまたぐ小さい読み取り | 通常の読み取りと同じ結果 |
| 一行ごとに読み取りを制御する入力 | 比較が終わる前に後続の全量を読み込まない |
| 出力の途中の読み取りエラー | 成功として扱わない |
| 参照プロセスの非ゼロ終了 | 有効な出力があっても失敗 |
| 足りない復元結果と余分なメタデータや入力ブロック | 順序または件数の検査で失敗 |
| 空の入力集合と一件の入力集合 | ファイルのバイト列が従来と一致 |
| 空白、改行、バックスラッシュ、非 ASCII を含む入力 | エスケープと改行が従来と一致 |

## テスト設計

`harfbuzz_serialize` のテストに、不変条件の番号を含む単体テストを先に追加する。
メモリ内の参照出力と小さい読み取り幅を使い、不変条件1と2を確かめる。
エラーを返す reader と失敗する小さい参照コマンドで不変条件3を確かめる。
不変条件4は、一時ファイルの全バイト列を従来のエスケープ式と比べる。
不変条件6は、空、一バイト、複数バイト、不正な UTF-8 を含む入力で、従来の生成式とのバイト列と順序の一致を確認する。
各配列の容量が長さと等しいことも検査する。
不変条件7は、同じ境界入力で arena の範囲を列挙した結果を個別の配列の生成式と比べる。
空のサイズと `usize::MAX` のサイズも計算し、後者が確保前のエラーになることを確かめる。

不変条件5は、同じ参照ツールとテストデータで実装前後の `serialization_agrees_with_harfbuzz` を実行して確かめる。
入力件数と比較件数のログを比較する。
次に適合テストの全体を2並列で走らせ、既存の比較を維持したことを確かめる。

同じ環境で、実装前後の当該実行ファイルの時間と子孫の合計 RSS を測る。
全体の2並列でも測り、単一の実行ファイルの結果と区別する。
変更後の CI の時間と RSS は、採択後に確認する。

## トレードオフ

行単位に処理すると、参照プロセスと比較が同時に進み、パイプの容量によって参照プロセスが待つ場合がある。
全出力を保持する必要はなくなるが、入力の全変異を作って重複を除く段階のメモリは残る。
ラスタライズなど、同時に走る別の実行ファイルの保持量もこの変更では減らない。
workflow 全体の最長経路への効果は、変更後の CI を実測するまで未確認とする。
