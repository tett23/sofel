# ADR 0054: HHEA と VHEA のメトリクス件数を32ビットで読む

ステータス: 採択

## 文脈

大文字の `HHEA` と `VHEA` は、横と縦のメトリクスのヘッダーである。
それぞれ、送り幅とサイドベアリングの両方を持つレコードの件数を格納する。
[ADR 0007](0007-sfnt-read-foundation.md) は横の件数を24ビットと定め、[ADR 0016](0016-font-and-vertical-metrics.md) は縦のヘッダーにも同じ読み取り処理を使うとした。

## 調査した事項

`sofel-read` の `Hhea::new` は、大文字の表でオフセット34から3バイトを読む。
`Vhea` はこの型の別名である。
テスト用の `hhea_wide` も件数を3バイトで書く。

一方、`sofel-subset` は大文字のヘッダーに38バイト以上を要求し、同じ位置で4バイトの件数を読み書きする。
HarfBuzz 15.1.0 の大文字のヘッダーは、この欄に32ビットの `MediumTypes::HBLUINT` を使う。

## 実装すること

`sofel-read` の横と縦の読み取り処理、切り詰めの診断、テスト用フォントの件数を32ビットにそろえる。
フォント経由の横と縦のメトリクス取得でも同じ件数を使う。
実装時に仕様書と README を更新し、ロードマップの判断結果を反映する。

## データ構造とアルゴリズム

大文字のヘッダーでは、オフセット34から4バイトをビッグエンディアンの符号なし整数として読む。
件数の戻り値には既存の `u32` を使う。
公開済みの読み取り関数と検証器では、既存の `CountWidth::U24` 引数で従来どおり大文字のヘッダーを選ぶ。
このヘッダー内では件数幅を4バイトとし、引数名の由来であるグリフ数の幅とメトリクス件数の幅を API 文書で区別する。
`CountWidth::U16` は小文字のヘッダーを選ぶ。
`MAXP` の読み取りでは引き続き `CountWidth::U24` を3バイトとして扱う。

## 実装しないこと

小文字の `hhea` と `vhea` の16ビット件数、`MAXP` の24ビットのグリフ数、メトリクス本体のレコード形式は対象外とする。

## 不変条件

1. 有効な先頭34バイトを持つ大文字のヘッダーで、件数の欄が4バイト以上読めれば、件数はその先頭4バイトをビッグエンディアンで解釈した値と一致する。
2. 同じ先頭34バイトの後に0〜3バイトしかなければ、読み取りはデータ不足を返し、検証器は必要長38と実際の表長を報告する。
3. 同じ先頭34バイトを持つ小文字のヘッダーでは、後続に2バイトあれば件数はその先頭2バイトの値と一致する。

| 表 | オフセット34以降のバイト（16進数） | 期待する結果 |
| --- | --- | --- |
| 大文字 | 空、`00`、`00 01`、`00 01 00` | データ不足 |
| 大文字 | `00 00 00 00` | 0件 |
| 大文字 | `00 01 00 00` | 65,536件 |
| 大文字 | `01 00 00 00` | 16,777,216件 |
| 大文字 | `FF FF FF FF AA` | 4,294,967,295件 |
| 小文字 | `00 01` | 1件 |

## テスト設計

`inv1_wide_metric_count` と `inv2_truncated_wide_metric_count` は表の大文字の例を横と縦の両方で試し、短い入力では診断の表タグも照合する。
`inv3_narrow_metric_count` は小文字の両表で16ビットの解釈を検査する。
`inv1_font_metrics` では、4バイトで1件と記したヘッダーと対応するメトリクス本体を使い、フォント経由で横と縦の送り幅を照合する。
実装前に、大文字の件数と37バイトの表の扱いでテストが失敗することを確かめる。

## トレードオフ

読み取りとサブセット化で件数の解釈が一致する。
従来のテスト用フォントのように件数を3バイトで終える大文字の表は、データ不足になる。
