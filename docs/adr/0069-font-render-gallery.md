# ADR 0069: フォントごとの描画見本をローカルと CI で生成する

ステータス: 採択（未実装）

## 文脈

開発者はコードを変更したとき、文字の輪郭や色がどう見えるかをフォントごとに確認したい。
手元で画像を開けるようにし、レビューする人も同じコミットをビルドせずに見本を読めるようにする。

## 調査した事項

[追加フォントの台帳](../../conformance/fonts.tsv)は13ファイルを識別子で区別する。
[README](../../README.md)に記された対象は TTC 内のフェイスを含めて57フェイスである。
[取得スクリプト](../../scripts/fetch-fonts.sh)と [CI](../../.github/workflows/ci.yml)には固定したフォントとライセンスを取得してキャッシュを検証する手順がある。
既存の `sofel-render` は1グリフを PGM または PAM で出力する。
[CI](../../.github/workflows/ci.yml) の起動条件はプルリクエストと main への push で、文書だけの変更はジョブを分けて扱う。

試作の短い文字列について、フェイス0を `sofel-shape -O json --no-glyph-names` でシェーピングした。
表の長さは空白を含む Unicode コードポイント数、右側の数は出力したグリフ数である。
横の送り幅は `--font-size=3072 --font-ppem=48` で得た `ax` の合計を64で割った値で、インクが占める幅とは異なる。
sbix だけは試作のビットマップ用サイズである109 ppem で測った。

| 対象 | 試作の入力 | 長さ → グリフ数 | 送り幅（px） | この入力で見るもの |
| --- | --- | ---: | ---: | --- |
| Arabic | مرحبا | 5 → 6 | 101.0 | 右から左に続く語の接続と点の配置 |
| Devanagari | नमस्ते | 6 → 5 | 101.4 | 子音の連なりと母音記号の位置 |
| Khmer | សួស្តី | 6 → 5 | 89.1 | 同じクラスタに属する字形の上下の配置 |
| Myanmar | မင်္ဂလာပါ | 9 → 7 | 185.7 | 複数のクラスタにまたがる字間と記号の配置 |
| Balinese | ᬩᬮᬶ | 3 → 3 | 116.1 | 最後の子音と母音記号を同じクラスタとして描いた形 |
| Hebrew | שלום | 4 → 4 | 100.0 | 右から左に組んだ語の字間と語末の字形 |
| Source Serif、Amstelvar | office & affix | 14 → 10 | 268.4、290.1 | 同じ文字列での ffi 合字の形と語の幅 |
| STIX Math | ∫₀¹ x² dx | 9 → 9 | 181.4 | 積分記号と、上付き・下付き文字の大きさと位置 |

両欧文書体で `--features=-liga` を付けると、同じ14コードポイントから14グリフを出力した。
三つのカラー形式では `simple_linear` がグリフ26になったが、試作で得た描画結果は空だった。
可変 COLR の2グリフも試作で得たのはグレーの輪郭である。

## 見本の長さと種類を選ぶ基準

一つのフェイスに単字と一行の文字列を並べる。
単字では輪郭を大きく見せ、文字列では隣り合う字の間隔やシェーピングによる形の変化を見せる。
書体間で比較する組には同じ入力と ppem を使う。
サイズがストライクで定まるビットマップの見本には、そのストライクの ppem を記す。
文字体系の異なる書体には、その書体で読み取れる語を使う。
数式用の書体には記号列を、カラー機能の試験用フォントには目的のグリフに解決される入力を使う。

長さは、見たい特徴が現れ、一覧の文字列欄に同じ縮尺で一行に収まる範囲で選ぶ。
試作の文字列欄は幅320 px で、欧文の長い方でも送り幅は290.1 px だった。
実装では字形の左右の張り出しも含めて収まりを確認する。
入力ごとにコードポイント数と描画幅の関係が異なるため、全文字体系に共通する文字数は定めない。
今回の語句と欄幅は一覧での目視比較を目的に選んだもので、可読性の実験から求めた最適値ではない。

## 実装すること

対象は台帳に載るフォントと、[ADR 0031](0031-diverse-font-corpus.md) が別に定める HarfBuzz の可変 COLR フォント（識別子 `hb-variable-colr`）とする。
後者は既存の `scripts/fetch-testdata.sh` が取得する固定版の `test/api/fonts/test_glyphs-glyf_colr_1_variable.ttf` を使う。
対象の全フェイスに、既定の可変軸座標で代表グリフの見本を用意する。
入力にはフェイスごとに固定した文字またはグリフ番号と ppem（1 em あたりの画素数）を使う。
文字はその書体が収録する文字体系から選び、文字指定が欠落グリフに解決されたら失敗とする。
フェイス番号は0から数え、TTC の各フェイスを個別に描く。
各見本はフェイス番号と入力を指定して `sofel-render` で描く。
カラーの見本には `--color` を指定する。
出力された PGM または PAM の画素を PNG に変換し、OS のフォントや別の描画エンジンで代用しない。

リポジトリ直下で `sh scripts/render-font-gallery.sh` を実行すると、フォントの取得と検証から画像の生成までを行う。
出力先は `target/font-gallery/` とし、毎回この実行専用の空の作業先から生成する。
単字の横には固定した文字列を `sofel-shape` の出力順、送り幅、オフセットに従って描く。
全フェイスの単字と文字列、入力、識別情報を一枚の一覧 PNG にまとめる。
成功時には一覧の `index.html` をブラウザーで直接開けるようにする。
HTML は一覧 PNG を相対パスで参照する。
画像の各欄にはフォント ID、フェイス番号、入力、ppem を添える。
現行の sofel が画素にできない形式には、対象と理由をケース単位で明記し、一覧に「未対応」と表示する。
未登録の失敗は未対応に分類せず、該当するフォント ID とフェイス番号を標準エラーに出して異常終了する。
未対応として登録する前に、固定入力で症状を再現する。
登録後も同じ入力で毎回描画を試みる。
登録した症状と結果が異なれば異常終了し、登録の見直しを促す。

CI では既存の変更判定で文書だけと判定した場合を除き、各プルリクエストの更新と main への push で同じコマンドを実行する。
成功した実行の HTML と一覧 PNG を、検査したコミットの SHA を名前に含む単一の Actions アーティファクトとして14日間保存する。
保存に失敗した場合もジョブを失敗とする。
実装時に README に生成手順と CI から取得して一覧を開く手順を記載する。

## 実装しないこと

OS にインストールされたフォントの列挙、全グリフの網羅、文章の組版、画像差分による合否判定、生成画像の Git への追加は行わない。

## 不変条件

1. 成功時の一覧にある（フォント ID、フェイス番号）の集合は対象の全フェイスと一致し、各組は一度だけ現れる。台帳が空なら失敗する。
2. 一覧 PNG の単字の描画領域は、同じ入力で得た PGM または PAM と寸法および表示色が一致する。未対応の組には理由を表示する。
3. 入力の取得失敗、未登録の描画失敗、PNG の書き込み失敗のいずれでも終了コードは非ゼロとなり、その実行を成功した見本として配布しない。
4. 一覧 PNG には各組の欄が一つずつあり、固定文字列の全グリフの描画範囲が指定した ppem の画素を等倍で配置したときにその欄に収まる。未対応のケースには理由を表示する。

| 入力 | 期待する結果 |
| --- | --- |
| 台帳が空 | 異常終了 |
| 描画できる単独フェイスが一つ | 一覧 PNG に一欄 |
| 二つのフェイスを含む TTC | 同じ ID のフェイス0と1が別の欄に現れる |
| 描画できる組と登録済みの未対応の組 | 前者に画像、後者に理由 |
| 前回の成功後にフォントの検証が失敗 | 異常終了し、前回の画像を今回の成果物に含めない |

## テスト設計

実装前に `inv1_gallery_faces` で空の台帳、単独フェイス、TTC を与え、一覧の組を期待値と照合する。
`inv2_gallery_pixels` でグレーとアルファ付きカラーの PNG をデコードして元の PGM または PAM の表示色と比較し、未対応の欄に理由があることを確かめる。
`inv3_gallery_failure` で不正なハッシュ、未登録の描画エラー、書き込めない出力先を個別に与え、終了コードを検査する。
`inv4_gallery_sheet` で合字とオフセット付きのグリフを含む入力を与え、各欄の画素と、一覧 PNG に各欄を配置した位置の画素が一致することを確かめる。
実装のプルリクエストでは、CI から成果物を取得して展開し、ネットワークを切ったブラウザーで一覧と画像を開く。
同じコミットで手元でも生成し、対象の組とデコード後の画素が一致することを確かめる。

## トレードオフ

代表グリフに絞ると、全フェイスを並べても変更前後の同じ文字を探しやすい。
選ばなかった文字や軸座標での崩れは見つけられないため、既存の適合テストは引き続き実行する。
保存期間を過ぎた見本が必要になったら、対象のコミットで生成し直す。
