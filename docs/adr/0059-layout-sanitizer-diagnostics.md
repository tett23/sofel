# ADR 0059: シェーピングで破損したレイアウト表を扱う規則を HarfBuzz に合わせ、検証時に結果を報告する

ステータス: 採択

## 文脈

GSUB はグリフの置換、GPOS は位置調整、GDEF はグリフの分類などに使う表である。
[ADR 0044](0044-shaping-conformance-exceptions.md) は、破損した表の読み方が HarfBuzz と異なる入力を `sanitize` の期待失敗に登録した。
フォントの作成者が修正量を見積もれるよう、1回の検証で破損箇所の一覧と件数、検査し切れなかった範囲を示す。
併せて、破損した表がシェーピングで使われるかどうかを知らせる。

## 調査した事項

`testdata.lock` が固定する HarfBuzz 15.1.0 の `OffsetTo::sanitize` は、オフセットを検査し、null でなければ参照先の検査結果を返す。
この関数は不正なオフセットをゼロに書き換えない。
`sanitize_blob` は表の検査に失敗すると空の blob を返す。
GSUB・GPOS の読み込みでは `lazy_some_gpos` を有効にしており、GPOS の一部の参照はこの段階ではたどらない。
GDEF の読み込みは既定のサニタイズコンテキストを使う。

`sofel-validate` は元のデータに対する診断をテキストまたは JSON で出力する。
診断には表タグ、表内のオフセット、重大度があり、JSON には診断の種類を識別する `kind` もある。
通常の検証は Error があれば終了コード1、警告だけなら0を返す。

## 実装すること

固定版 HarfBuzz のシェーピングで用いる GSUB、GPOS、GDEF のサニタイズ規則を移植する。
同一フェイスのシェーピング、レイアウト選択、検証器で、表を採用するか破棄するかの判定を共有する。
検証器は元のバイト列を引き続き検査し、それとは別に、サニタイズで実在する表を破棄したときに、その表をシェーピングで無視する旨を報告する。

表の破棄を伝える診断は Warning とし、JSON の `kind` を `layout_table_discarded` とする。
表全体に対する診断なので、オフセットは表の先頭の0とする。
たとえば GSUB を破棄するときは、テキストと JSON のメッセージを `shaping ignores the GSUB table after sanitization failed` とする。
この Warning はシェーピングでの扱いを知らせる互換性の注記とする。
[ADR 0007](0007-sfnt-read-foundation.md) による個々の構造診断には元の重大度を使う。
実装時に README、仕様書、検証コマンドのヘルプに診断の意味を記し、ロードマップの移植項目に結果を反映する。

## データ構造とアルゴリズム

フェイスごとに各表の不在、採用、サニタイズによる破棄を区別する。
入力のバイト列を保持したまま、シェーピングには採用した表のビューだけを渡す。
HarfBuzz が読み込み時に検査する範囲、遅延して検査する範囲、走査量と再帰の制限を対応する読み取り経路に反映する。
一部の参照を使えないまま表を採用する場合と、表全体を破棄する場合を区別する。
検証器はフェイスと表の組ごとに、表の破棄について最大1件の注記を生成する。

### 一度の検証で修正箇所を列挙する

元データの構造検査は、サニタイザが最初の破損で表を破棄しても続ける。
個別に位置を確定できるフィールド、兄弟レコード、独立した参照先、残りの対象表とフェイスを検査し、安全に確認できた破損をすべて報告する。
範囲外の参照は、入力中の参照元フィールドの位置と理由を報告する。
参照先の境界を確定できなければ、その枝は未検査として参照元と理由を示し、位置を確定できる次の枝に進む。
既存の走査量の上限に達した場合も、対象表と打ち切り理由を示す。

テキストと JSON の双方で、破損ごとにフェイス、表タグ、表内のバイト位置、理由を出す。
検証の末尾には対象3表について、確認した破損箇所数と検査の完了・未完了を出す。
箇所数はフェイス、表タグ、バイト位置の組を数える。同じ場所を複数の経路から参照しても1箇所とし、同じ位置で異なる理由を確認したときは理由をすべて残す。
互換性の注記と打ち切り通知は破損箇所数に含めない。
未検査の枝があれば「少なくとも N 箇所」とし、未検査範囲と理由を併記する。JSON にも同じ件数、完了状態、未検査範囲を機械的に取得できる形で載せる。

## 実装しないこと

入力ファイルの修復、サニタイズ済みフォントの書き出し、他の表に対するサニタイザの移植は対象外とする。
サニタイズ以外の理由で表が使われない場合は `layout_table_discarded` の対象外とする。

## 不変条件

1. 各フェイスの各対象表について、シェーピングでのサニタイズによる採否は固定版 HarfBuzz の対応するサニタイズ段階の結果と一致する。サニタイズ後のブロックリスト判定はこの比較から除く。
2. 各フェイスの各対象表について、`layout_table_discarded` の件数はサニタイズで破棄したときに1、それ以外は0である。テキストと JSON の表タグ、オフセット、重大度は一致する。
3. 元のバイト列に対する診断は引き続き得られる。追加する Warning だけでは終了コードは変わらない。
4. 安全に検査できる独立した破損が N 箇所あれば、1回の検証で全 N 箇所の位置と理由が出る。未検査範囲がある場合、確認済み件数は下限として報告される。

| 入力 | 表の破棄を伝える注記 |
| --- | --- |
| 対象表がない、またはすべて採用 | 0件 |
| 不正な参照があっても HarfBuzz が表を採用 | その表について0件 |
| GSUB だけをサニタイズで破棄 | GSUB に1件 |
| 同じ表に複数の破損があって表を破棄 | その表に1件 |
| 同じフェイスで GSUB と GPOS を破棄 | 各表に1件 |

## テスト設計

`inv1_layout_sanitization` で、GSUB、GPOS、GDEF ごとに有効な表、ちょうど収まる参照、1バイトあふれる参照を生成し、固定版の対応する読み取り経路と採否を照合する。
手元の参照実装で表を採用する例と破棄する例を確かめてから期待値を固定する。
[ADR 0044](0044-shaping-conformance-exceptions.md) のシェーピング1件、レイアウト選択3件、無作為な文字列のシェーピング3件はそれぞれ実行し、一致を確認した項目から期待失敗を外す。

`inv2_layout_discard_diagnostic` で境界表の各ケースと複数フェイスを検証し、テキストと JSON の件数と内容を比較する。
`inv3_original_layout_diagnostics` で既存の診断の種類、位置、重大度と終了コードを照合する。
`inv4_all_layout_damage` は同じ表の別レコードと別表に独立した破損を計3箇所作り、1回の CLI 実行で3箇所すべての位置と理由、集計が出ることをテキストと JSON の各モードで検査する。
同じ破損を指す参照が二つある例、参照先を読めない枝の後にも破損がある例、走査上限に達する例では、重複計上、見落とし、総数の誤表示を検出する。
実装前には個別の破損、集計、表の破棄の注記をそれぞれ独立して期待値と照合し、欠けている項目でテストが失敗することを確かめる。

## トレードオフ

表を読めるかどうかの判定を共有すると、検証時に伝えた結果をシェーピングで再現できる。
検証時には元データの診断と互換性の判定の両方が必要になり、破損した表について出力する診断も増える。
