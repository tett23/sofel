# ADR 0049: HVARの表参照を一度にし、送り幅を呼び出し側でキャッシュする

ステータス: 採択（未実装）

## 文脈

[ADR 0029](0029-variation-deltas.md) は、HVARの送り幅について領域係数を`Location`に保持し、グリフごとの送り幅キャッシュを後回しにした。[ADR 0027](0027-variable-fonts.md) は、送り幅キャッシュを呼び出し側が持つ値として後続のADRに委ねた。ライブラリの値を不変に保ち、キャッシュを呼び出し側が持つという[仕様](../specifications.md)は維持する。

現行の`Instance::advance_with_scratch`は、HVARを開いて送り幅のDeltaSetIndexMapを得た後、差分の評価でHVARをもう一度開く。HVARの表参照を一度にした未コミットの試作を、macOS aarch64のreleaseビルドで2026-11-11に計った。30標本、3回の予熱、標本ごとに10 ms以上を測る`bench/src/harness.rs`の設定で、`CARGO_INCREMENTAL=0 CARGO_PROFILE_RELEASE_DEBUG=0 cargo run --release --manifest-path bench/Cargo.toml -- --filter 'advance ' --testdata target/testdata`を、元の実装、試作、試作、元の実装の順に走らせた。

全グリフを順に問い合わせる時間は、RobotoFlex-Variableで89.05→88.80 µs（0.3%短縮）、SourceSerifVariable-Romanで64.55→57.70 µs（10.6%短縮）、AdobeVFPrototypeで15.80→13.75 µs（13.0%短縮）だった。同一グリフの繰り返しはそれぞれ93.20→91.70 µs、60.75→57.80 µs、13.50→12.80 µsだった。これらはローカルの試作値で、CI上の再現は未確認である。

さらに、同じ試作で、128枠の直接写像キャッシュと全グリフの配列を比べた。`CARGO_INCREMENTAL=0 CARGO_PROFILE_RELEASE_DEBUG=0 cargo run --release --manifest-path bench/Cargo.toml -- --filter 'advance cache' --testdata target/testdata`では、128枠の配列は1024バイトで、全グリフ順次の空振りは3フォントとも全件だった。全グリフ配列の確保量はRobotoFlex-Variableで24+7576バイト、SourceSerifVariable-Romanで24+11448バイト、AdobeVFPrototypeで24+2504バイトだった。128枠のヒット単体は約1.29 ns、最初の問い合わせは送り幅の計算と配列の初期化を含めて約70〜114 nsだった。この試作は位置の照合とシェーピングを含まない。

実テキストでのヒット率は、同じ3フォントを`wght=500`に置き、`react-dom.txt`と`en-thelittleprince.txt`をsofelでシェーピングして調べた。コマンドは`SOFEL_CACHE_REAL_TEXT=1 CARGO_INCREMENTAL=0 CARGO_PROFILE_RELEASE_DEBUG=0 cargo run --release --manifest-path bench/Cargo.toml -- --filter 'advance cache' --testdata target/testdata`で、追加した観測コードは未コミットである。シェーピング後のグリフID列と、`ShapeFont::h_advance`が実際に問い合わせたID列の両方で数え、6組すべてで問い合わせ数とヒット数が一致した。行ごとに128枠を作り直す場合と、文章の全行で一つを保持する場合を分けた。全グリフ配列は、文章の全行で一つを保持した。

## 実装すること

1. HVARとVVARの送り幅を求めるとき、各表を一度開いて、DeltaSetIndexMapとItemVariationStoreのビューを同じ表から得る。既存の丸めと不正な表の扱いは変えない。
2. `sofel-font`に、特定の`Instance`を保持する、呼び出し側所有の水平送り幅キャッシュを追加する。既存の`Instance::advance`と`advance_with_scratch`はキャッシュを作らない。キャッシュの問い合わせは必要な場合だけ`advance_with_scratch`を呼ぶ。異なるフォントまたは位置にキャッシュを転用するAPIは設けない。
3. シェーピングでは、非既定位置の呼び出しが使う`Instance`からキャッシュを作り、水平送り幅の問い合わせで使う。既定位置ではキャッシュの128枠を初期化せず、水平送り幅もキャッシュを通さない。既存の`GlyphScratch`はgvarの作業領域として併用する。キャッシュの寿命は一回のシェーピング呼び出しまでとする。文章の全行で保持するAPIは、このADRでは追加しない。
4. 全グリフ順次、同一グリフ繰り返し、`react-dom.txt`、`en-thelittleprince.txt`について、キャッシュなし、128枠、参照のHarfBuzzの送り幅とシェーピングの時間をreleaseで測る。既定位置と非既定位置の結果を記録する。実装による既定位置の退行と、1回のシェーピングあたりのキャッシュ初期化費用を分けて報告する。
5. 実装後、[docs/specifications.md](../specifications.md)と[README.md](../../README.md)の送り幅キャッシュと計測に関する記述を更新する。

## 実装しないこと

縦送り幅、縦原点、gvarの輪郭・幻の点、GDEFのVariationIndex、MVARの値はキャッシュしない。`Location`と`Font`への内部可変性は加えない。全グリフ数に比例する配列や`malloc`・`mmap`のアリーナは使わない。現行の`Instance::advance`の公開シグネチャは変えない。

## データ構造とアルゴリズム

キャッシュは128枠の直接写像とする。各枠は`(glyph_id: u32, advance: u32)`を持ち、空の枠のIDを`u32::MAX`とする。グリフIDを128で割った余りの枠を読む。同じIDなら値を返す。異なるIDなら、その`Instance`の`advance_with_scratch`を一度呼び、計算が終わってから枠全体を一度書き換える。`u32::MAX`を問い合わせた場合は枠を使わずに計算し、空の印と衝突させない。キャッシュは`Instance`を値として保持し、別の位置に付け替えられない。したがって、位置を照合するためのハッシュや座標の複製を問い合わせごとに使わない。

キャッシュの用途は水平送り幅だけとする。HVARの差分があってもgvarの幻の点によるfallbackでも、格納するのは丸めを終えた`u32`の最終結果である。`Instance`ごとに新しいキャッシュを作るため、同じグリフIDが別の位置で異なる値を持っても混ざらない。

## 不変条件

1. **ADR0049-I1**: 任意の有効なフォント、位置、`u32`のグリフID列で、キャッシュの各問い合わせは同じ`Instance`の`advance_with_scratch`と同じ`u32`を返す。衝突と空振りは値を変えない。
2. **ADR0049-I2**: キャッシュは構築に使った`Instance`のフォントと位置だけを問い合わせる。異なる`Instance`のために新しく作ったキャッシュは、前のキャッシュの値を再利用しない。
3. **ADR0049-I3**: HVARまたはVVARの表を一度に開いた送り幅は、元の実装の値と同じである。表が無い場合、不正な場合、位置が既定の場合も同じである。
4. **ADR0049-I4**: シェーピングのグリフID、クラスタ、フラグ、位置は、キャッシュを使わない同じ`Instance`の結果と一致する。既定位置では128枠を初期化しない。

| 境界入力 | I1・I2 | I3 | I4 |
| --- | --- | --- | --- |
| 空の列、空のテキスト | 値を作らない | 参照しない | 空の結果 |
| 既定位置のテキスト | 値を作らない | 従来の値 | 128枠を初期化せず同じ結果 |
| 1件を一度と二度 | 二度目は同じ値 | 同じ値 | 同じ結果 |
| 128件が異なる枠にちょうど収まる | すべての二度目がヒット | 同じ値 | 同じ結果 |
| 129件目が最初の枠と衝突 | 再計算した値が一致 | 同じ値 | 同じ結果 |
| `u32::MAX`のグリフID | 枠を使わずに同じ値 | 同じ値 | 対象外 |
| 同じグリフ、異なる位置またはフォント | 新しいキャッシュで別々に計算 | それぞれ同じ値 | それぞれ同じ結果 |
| HVAR/VVAR無し、壊れたmapまたはstore | fallbackの値を保存 | 以前の値と一致 | 同じ結果 |

## テスト設計

最初に`ADR0049-I1`から`ADR0049-I4`までの名前を含むテストを書き、追加するAPIを使うテストが現行コードで失敗することを確かめる。`ADR0049-I1`では手で組むHVARとgvarのフォントを使い、空、一つ、同じIDの反復、異なる枠の128件、衝突する129件、グリフIDの末尾と`u32::MAX`を調べる。各問い合わせをキャッシュなしと比べ、空振りとヒットの回数も調べる。

`ADR0049-I2`では、同じフォントの既定位置と`wght=500`、別フォントの同じグリフIDで、キャッシュが別々の`Instance`に結びつくことを調べる。`ADR0049-I3`では、HVARとVVARそれぞれについてmapあり・なし、storeあり・不正、位置が既定・非既定の組を、変更前の期待値とHarfBuzzの参照値で調べる。

`ADR0049-I4`では短文、同じ文字の繰り返し、合字を含む行、空行を既定位置と`wght=500`でシェーピングし、キャッシュなしと全フィールドを比べる。既存の参照コーパスでも、HarfBuzzの期待する失敗の件数が増えないことを確認する。

速度は「実装すること」4の項目をベンチマークで調べる。128枠の初期化と、行をまたいで持てないことが十分な速度の改善を妨げる場合は、実測結果を残し、別のADRで寿命か構造を再検討する。

## トレードオフ

128枠の配列は固定の1024バイトをシェーピングの呼び出しに足す。全グリフ順次は実測で全件空振りになり、最初の問い合わせと枠の初期化も費用となる。一方、実テキストでは一回の行内でも62.51〜70.50%がヒットした。行をまたぐ保持なら98.50%以上だったが、現在のシェーピングAPIでその寿命を足すと呼び出し側の状態とAPIが増えるため採らない。

全グリフ配列は連続した文章のヒット率を最大1.49ポイント上げる一方、観測したフォントで2.5〜11.4 KiBを使う。128枠の配列はグリフ数によらず1 KiBで、短い行での初期化量も一定である。どちらも、保持する`Instance`の領域は別に要る。キャッシュを任意の`Instance`に付け替えない設計はAPIの柔軟性を減らすが、位置ごとの値の混同を型の所有関係で避ける。
