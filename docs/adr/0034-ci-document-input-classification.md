# ADR 0034: CIを省く文書を用途とパターンで登録する

ステータス: 採択

## 文脈

[ADR 0032](0032-documentation-only-ci.md) は、`docs/` 以下と各階層のREADME.md、CONTRIBUTING.mdを、パスだけでCIのビルドとテストの省略対象にした。
その後の運用規則では、ビルドやテストの入力、コード、依存関係、設定、workflowは省略せず、拡張子やdocs配下であることだけで判断しないと定めた。
たとえば、Markdownでも `include_str!` で埋め込むものやテストの期待値に使うものは入力である。

一方、ADRを一つ追加するたびにファイル名を一覧へ登録する方式では、管理する一覧が増え続ける。
利用者のレビューを受け、用途を確認したディレクトリやglobをまとめて登録できる方式にする。
パターンは用途を表す登録規則として使い、拡張子だけから文書であると推測しない。

## 実装すること

### 文書と入力の登録

`ci/documentation-only.rules` に、`document` または `input` とパターンを、タブで区切って一行ずつ登録する。
`document` はビルドとテストを省いてよい文書、`input` は必ず通常CIを実行する入力である。
同じパスが両方に一致した場合は、行の順序によらず `input` を優先する。
どちらにも一致しないパスは通常CIの対象とする。

`document` の登録時には、その範囲がプロダクトのビルド、コード生成、テスト、期待値の読み込み、ベンチマークの入力でないことを、コードと実行コマンドから確認する。
範囲の一部が入力なら、具体的なパスまたはパターンを `input` として登録する。
コード、依存関係、設定、workflowを `document` の有効範囲に含めない。
常時実行する文書検査やadr-guardへの入力であることは、`document` への登録を妨げない。

READMEとCONTRIBUTING（拡張子なし、`.md`、`.rst`など）も用途を確認して対象に含める。
説明用の図や監査、性能計測の記録も、プログラムの入力でない範囲をまとめて登録してよい。
初期登録では、現在のdocs内の用途とREADMEを調べ、ADRと記録の追加を個別のファイル名の追記なしに扱えるパターンを選ぶ。
未確認の範囲を全リポジトリ共通の `*.md` で省略する規則は作らない。

文書をプログラムの入力として使う変更には、そのパスを `input` に登録する変更を含める。
この対応はコードレビューの確認項目にする。
任意のプログラムが動的に組み立てるパスの依存関係を、静的解析で完全に検出できるとは主張しない。

### パターンの形式

パターンはリポジトリ相対パスに対するBashの `case` のglobとする。
`*` は空を含む任意の並びで、`/` も含む。
`?` と角括弧の文字集合もBashの規則に従う。
`**` に専用の意味を与えず、`*` と同じにする。
末尾が `/` のパターンは、その末尾に `*` を加えてディレクトリ以下を表す。
たとえば `docs/adr/` は配下全体、`docs/adr/*.md` は配下のMarkdownを表す。

パターンをシェルコードとして `eval` せず、ファイル展開もしない。
ロケールは `C` に固定し、拡張globは使わない。
空行と `#` から始まるコメント以外は、規定の2列を必要とする。
未知の種別、空のパターン、絶対パス、`.` または `..` のパス要素、重複行、余分なタブは不正とする。
規則ファイルは改行区切りであり、改行を含むパターンは登録できない。
変更パス自体は [ADR 0032](0032-documentation-only-ci.md) のとおりNUL区切りで扱う。

### 判定の優先順位

規則は変更前の比較起点のコミットから読む。
pull requestではmerge-base、pushではbeforeを比較起点とする。
規則自体の変更は設定の変更として、内容にかかわらず通常CIにする。
そのPRで追加した省略規則によって、そのPR自身のビルドを省くことはできない。

差分が空でなく、すべての変更パスが `document` に一致し、どのパスも `input` に一致しない場合だけ `docs_only=true` とする。
規則がない、読めない、不正である場合は通常CIを実行する。
Git差分処理自体が失敗した場合は、[ADR 0032](0032-documentation-only-ci.md) と同じく判定ジョブを失敗させる。
移動は変更前後の両パスについて判定する。

新規ADRや記録が既存の文書パターンに一致すれば、個別登録なしでビルドとテストを省く。
ただし、文書検査とadr-guardは常に実行する。
監査や性能計測の記録が `document` に一致していても、コミット後の変更、削除、移動を許可しない。

実装PRでは、[ADR 0032](0032-documentation-only-ci.md) のステータスに「→省略する文書の判定は [ADR 0034](0034-ci-document-input-classification.md)」を追記する。
READMEと仕様書に、用途の確認、入力の優先、未知のパスと規則の更新は通常CIになることを記載する。
[ADR 0032](0032-documentation-only-ci.md) の比較範囲、常時実行する保護検証、ジョブの依存関係、結果の集約は維持する。

## 実装しないこと

- `docs/` 以下や `.md` であることだけを根拠に、用途を調べず省略規則を登録すること。
- 未確認の範囲を自動で文書に分類すること。
- 任意のビルドスクリプトの依存関係を完全に推論する仕組み。
- 文書の検査と、ADR、監査、性能計測の記録の保護を省くこと。

## 不変条件

1. **I01**: 有効な規則と空でない差分がある場合、規則ファイル自身の変更がなく、全パスが `document` に一致し、一つも `input` に一致しないことと、`docs_only=true` は同値である。
2. **I02**: `input` に一致したパスを含む差分は、規則の行順や `document` との重複によらず通常CIになる。
3. **I03**: 未知のパス、規則の追加または変更、規則の欠落や不正、空の差分は通常CIになる。
4. **I04**: `docs_only` の値によらず、文書と変更禁止の記録の検証を実行する。

| 境界の入力 | 判定 |
|---|---|
| 用途を確認して登録したREADME、README.md、CONTRIBUTING.md | 文書だけ |
| `document docs/adr/` に一致する新規ADR | 文書だけ。個別登録不要 |
| 文書パターンに一致しない未知のファイル | 通常CI |
| 文書パターン内の `input docs/fixture.md` | 通常CI |
| 同一パスに両種別が一致し、行順を逆にする | どちらも通常CI |
| 登録済み文書とCargo.tomlまたはworkflow | 通常CI |
| 新規文書と規則への登録 | 通常CI |
| 規則なし、不正な規則、空差分 | 通常CI |
| 文書から入力または未知の名前への移動 | 通常CI |
| 登録済み監査記録の削除 | ビルドを省くが、保護検証は失敗 |
| 空白、改行、シェル特殊文字を含む変更パス | パスを分割せず、コードとして実行せず判定 |

## テスト設計

一時GitリポジトリでI01からI03の境界表を先にテストし、旧来のdocs配下一律判定では `input` のケースが失敗することを確認する。
テスト名には不変条件の番号を入れる。
headで規則を追加してもそのPRを省略できないこと、Bashの特殊文字を含むパスをコードとして実行しないことも検証する。
ディレクトリ指定、`*`、`?`、文字集合、末尾スラッシュ、複数階層について定義した一致を検証する。

I04は [ADR 0032](0032-documentation-only-ci.md) の保護テストとworkflowの集約テストを維持して確認する。
テスト入力をdocsに置いたfixtureを `input` に登録し、そのfixtureだけの変更でも通常CIになることを確認する。
初期規則のレビューでは、コードとビルドコマンドの検索範囲と、入力でないと判断した根拠をPRに記載する。

## トレードオフ

用途が同じ文書をディレクトリやglobでまとめるため、新規ADRの個別登録は不要になる。
一方、その範囲にプログラムの入力を新しく置く場合は、`input` への登録を忘れない運用が必要になる。
完全な依存解析を導入するより、明示的な用途の規則とレビューで小さく保つ方針を取る。

Bashのglobでは `*` がパス区切りも含むため、ファイルシステムのglobと同じと思い込まないよう、規則とテストで意味を固定する。
Gitの差分をNUL区切りで読む処理もBashを使うため、別のパターン処理ライブラリは導入しない。
