# 直列化の適合テストの保持量の削減

2026年11月11日に、[ADR 0035](../adr/0035-stream-serialization-reference-output.md) の提案をローカルで比較した。
基準は commit `7707f3f499a74afe6ed9687e1ed6f7d2e20aa296` で、ライブラリ本体と参照ツールを変えず、直列化の適合テストのデータ構造と入出力を変えた。
ADR と実装は未コミットで、変更後の CI は未実測である。

## 条件と測り方

Apple M1 Max、メモリ64 GiB、macOS 27.0（26A428）、Rust 1.99.0を使った。
Rust のビルドは `CARGO_BUILD_JOBS=4 CARGO_INCREMENTAL=0` とし、release のビルド済みの実行ファイルを測った。
時間の測定中は、ほかの担当に Cargo と C のビルドを待ってもらった。
参照用の `hb-dump`、フォントと入力のテキストは前後で同じものを使った。

時間は `/usr/bin/time -p` の `real`、メモリは `scripts/measure-process-tree.sh` の `peak_tree_rss_kib` で比較した。
メモリの値は起動したコマンドと子孫の RSS の合計の最大観測値である。
共有ページを重複して数え、採取の間の瞬間的な最大値は取り逃す。
物理メモリの最大使用量と同一ではなく、仮想アドレス空間の予約量でもない。

単体の比較には、固定して保存した変更前後の実行ファイルで、同じ既存テストを選んだ。
追加した単体テストの時間は含めない。

```sh
/usr/bin/time -p sh scripts/measure-process-tree.sh TEST_BINARY \
  serialization_agrees_with_harfbuzz --exact --nocapture --test-threads=1
/usr/bin/time -p sh scripts/measure-process-tree.sh \
  env CARGO_BUILD_JOBS=4 CARGO_INCREMENTAL=0 sh scripts/test-conformance.sh 2
```

## 保持量の根拠

変更前の全体2並列の途中から、子孫プロセスの内訳も採取した。
その観測中の最大値1,534,208 KiBでは、`raster` が767,632 KiB、`harfbuzz_serialize` が762,240 KiB、参照用の `hb-dump` が3,072 KiBだった。
これは途中からの観測であり、全期間の最大値ではない。
この内訳から、まず直列化のテスト側の保持量を調べた。

変更前のテストに診断の出力を一時的に加え、各段階の `len` と `capacity` を数えた。
次の表は最初のフォント `adwaita.ttf` の値である。
時間と RSS の比較は診断の出力を加えていない実行ファイルで行った。

| データ | 件数 | 実際のバイト数 | バイト配列の容量の合計 |
| --- | ---: | ---: | ---: |
| 生成した全変異 | 228,462 | 179,013,182 | 325,753,605 |
| 並べ替えて重複を除いた入力 | 195,624 | 168,167,093 | 305,846,154 |
| エスケープして連結した入力全文 | 対象外 | 168,433,442 | 未計測 |
| 参照出力の全文 | 対象外 | 223,507,261 | 未計測 |

変更前は、後半の三つを比較中も同時に保持していた。
挿入変異では元の配列を複製した後に `insert` するため、容量の拡張と後半の移動も起きていた。
生成時の `Vec<Vec<u8>>` の外側の容量は253,952要素で、64 bit 環境の24 byte の `Vec` だけで約6.1 MBになる。

最初の変更は、変異を必要な容量へ一度だけ書き、入力を `BufWriter` へ逐次書き込み、参照出力を再利用する一行のバッファで比較するものだった。
全入力を連結した文字列と参照出力の全文をなくし、生成後の入力も参照プロセスの起動前に解放した。

次の変更は、不変な byte arena と範囲の索引である。
全変異の必要なバイト数と件数を先に計算し、それぞれ一つの `Vec` に容量を確保した。
バイト列は書き換えず、範囲の索引だけを並べ替えて重複を除いた。
arena のバイト容量は179,013,182、索引の容量は228,462範囲となり、個別のバイト配列の確保をなくした。
重複したバイト自体は arena に残るため、この量は重複を除いた入力の168,167,093 byte より大きい。

## 単体の時間と RSS

まず変更前と個別の `Vec` を使う逐次版を続けて測り、その後で逐次版と arena 版を続けて測った。
各行は1回の測定で、複数回の平均ではない。

| 方式 | 時間 | 合計 RSS の最大観測値 |
| --- | ---: | ---: |
| 変更前の一括保持 | 24.52秒 | 857,712 KiB |
| 個別の `Vec` と逐次処理 | 16.13秒 | 306,720 KiB |
| 個別の `Vec` と逐次処理の再測定 | 16.03秒 | 306,848 KiB |
| byte arena と逐次処理 | 15.73秒 | 187,584 KiB |

最初の変更前の測定と arena 版を比べると、時間は35.8%、合計 RSS の最大観測値は78.1%減った。
同じ比較の組の個別 `Vec` 版から arena 版への RSS の削減は38.9%だった。
この組の時間差は0.30秒で、各1回の測定から arena 単独の速度の優位までは判断しない。
メモリの差が大きく、ケースも一致したため、提案の実装には arena 版を選んだ。

## 全体の2並列実行

適合テスト全体も同じ runner で2並列にして確認した。
変更前の最初の行には、RSS の内訳を調べる追加の観測も途中から含む。
その追加処理の時間も含まれるため、平均値にはまとめない。

| 方式 | 時間 | 合計 RSS の最大観測値 |
| --- | ---: | ---: |
| 変更前、追加観測あり | 130.53秒 | 1,780,912 KiB |
| 変更前、追加観測なし | 124.20秒 | 2,227,296 KiB |
| 個別の `Vec` と逐次処理 | 102.76秒 | 1,931,488 KiB |
| byte arena と逐次処理 | 123.76秒 | 1,955,392 KiB |

全体の観測値は実行ごとに変動し、arena 版で全体の時間や RSS が減ったとは断定しない。
同時に走るテストの組と runner の状態の影響は分離していない。
確認できた改善は直列化のテスト単体の保持量と時間であり、変更後の CI の workflow 完了時間は採択後の確認に残る。

## 出力とケースの一致

旧方式の生成式と arena で作った全入力を、件数と各バイト列の順序で比較した。
`adwaita.ttf` は195,624件、168,167,093 byte、`SourceSansPro-Regular.otf` は179,171件、132,396,723 byteで、すべて一致した。
これは件数やハッシュだけの比較ではなく、各バイト列の一致を検査したものである。
この照合は診断用に一時的に加えて実行し、時間と RSS の測定からは外した。

5フォントの既存の比較件数と生成した入力件数を示す31行のログも、変更前後で一致した。
全体の計測時点で実行したテストの名前を数えると、変更前の65件はすべて残り、6件の単体テストを追加した71件が成功した。
その後の精読で、読み取りの区切りごとの同じ結果を直接比較するテストを1件追加した。
`cargo test --release -p sofel-conformance --test harfbuzz_serialize adr0035_i1_reader_chunk_boundaries -- --test-threads=1` は1件成功し、通常の読み取りと容量1、2、7、8192のバッファで結果が一致した。
この追加テストは上記の全体の時間と RSS の測定には含まれない。
`cargo clippy -p sofel-conformance --test harfbuzz_serialize -- -D warnings`、`cargo fmt --all -- --check`、`adr-guard links --fix` と `git diff --check` も成功した。
参照出力の不足、余分な行、読み取りエラー、参照プロセスの失敗は先行テストに加えた。
旧方式では変異の配列の容量が長さに一致するテストが失敗し、必要な容量への一度の書き込みの後に成功した。

## 残る候補と限界

mmap で領域を予約し、自前で管理する arena は未実測である。
この変更では、通常の `Vec` の事前確保で大きなバイト領域と索引を作り、新しい unsafe を使わなかった。
mmap を導入する場合は、仮想アドレスの予約量と resident なページの量を分け、実時間の改善を確かめる必要がある。
ライブラリ本体の `no_std` と wasm には変更を加えていない。

ラスタライズの参照出力の保持と、C ビルドの巨大な翻訳単位は残る候補である。
この変更では native と wasm の C ビルドを並列のまま維持し、コンパイラの最適化レベルも変えない。
CI の C ビルドで観測した RSS の増加が解消したとは判断しない。
